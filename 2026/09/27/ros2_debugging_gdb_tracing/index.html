ROS 2 排障笔记：GDB、日志与 Tracing

文章目录

ROS 2 的软件问题可以先分成四类：节点退出了、节点卡住了、节点收不到数据、节点运行得太慢。 它们需要不同的证据。GDB 看进程停下来的调用栈和变量，日志记录业务经过，ros2 tracing 记录运行过程中的事件时间线；strace 看系统调用，perf 找 CPU 热点。先问清楚想证明什么，再选工具，会比同时打开所有工具更容易定位问题。

本文以 Ubuntu 22.04 + ROS 2 Humble + C++ / rclcpp 为操作基线，资料核对日期为 2026-09-27。命令在 Linux 的 Bash 中执行；macOS 用户应进入 Linux 容器或虚拟机。Jazzy、Rolling 的 tracing 子命令和默认配置可能不同，不能把新版本文档的命令直接当作 Humble 命令。

随文提供一个包含“正常、异常、慢回调”三种模式的最小示例包。示例编译与 GDB 验证结果见验证记录；tracing 部分给出官方配置流程及教学时间线，教学数字不是本站机器的 tracing 实测结果。

一、按现象选择工具

现象 先做什么 工具能回答的问题 不能据此直接判断
节点突然退出、segfault、abort 保存日志、GDB / core 停在哪一行？调用链和变量是什么？ 崩溃位置一定是最早写坏内存的位置
进程还在，但没有输出 CPU / 线程状态、所有线程栈 在计算、睡眠、等锁，还是等响应？ 栈里出现 futex 就是死锁
topic 有名字，但收不到消息 图、类型、QoS、域、发现 发布者与订阅者是否真的匹配？ topic list 有名字就说明数据链路正常
频率下降、偶尔卡顿 tracing，再按证据用 perf 哪个回调耗时？何时开始和结束？ 回调耗时长一定是 CPU 计算多
随机内存错误 ASan / UBSan，再回到 GDB 越界、释放后使用等发生在哪里？ 一次无报错就证明没有内存问题
相同输入偶发不同结果 rosbag 固定输入、保留参数和版本 改动前后是否能稳定比较？ bag 重放能复刻原来的线程调度

backtrace 与 tracing 不是同一件事。 前者是暂停时的函数调用栈；后者是不断记录事件，结束后再按时间分析。ROS 2 提供了日志、CLI 和 tracing 的集成入口；GDB、LTTng、perf 则是更通用的工具。

对真实机器人，GDB 断点会暂停控制进程；练习时先在仿真或脱离执行机构的环境进行。测性能时撤掉断点，并记录日志和跟踪配置，避免把调试开销误当成系统原有的延迟。

三、日志：先知道程序走到了哪里

3.1 配置级别和输出位置

diagnostic_demo:=debug 指定 logger 名称；不确定名称时先用 --log-level debug。logger 名称通常与节点名相关，代码也可以创建子 logger。没有在编译产物中保留的日志，运行时调高等级也无法恢复。

默认日志目录通常是 ~/.ros/log，也会受 ROS_HOME 影响；这里通过 ROS_LOG_DIR 显式指定。控制台、磁盘日志和 /rosout 是不同输出路径；ros2 launch 还会管理自己的进程日志，不应假定所有信息都在同一个文件。图形环境可用 ros2 run rqt_console rqt_console 按节点和级别筛选 /rosout。日志配置文档

六、卡死与 core：没有正常退出提示怎么办

6.1 进程还活着：观察线程，再 attach

Linux 中先用 ps -eo pid,ppid,pcpu,stat,args 找到真正的节点或承载进程。不要把 ros2 launch 的 Python 父进程当成目标。

在 GDB 中：

attach 通常会暂停目标。detach 放开进程，使其继续运行；采第二次快照前必须先让程序运行一段时间，不能对暂停的进程连续看两次栈就宣称“栈一直不变”。

栈／CPU 现象 下一步核查
高 CPU，栈常在自己的循环或算法 查循环边界、输入规模；用 perf 找热点
sleep、poll、epoll_wait 可能正常等待；核对预期输入和超时
futex、mutex、condition variable 找等待对象、持有者和唤醒条件；一次采样不能证明死锁
回调里 future.wait()，响应一直不处理 检查 Executor 线程和 callback group

ROS 2 常见自锁链路是：定时器回调持有互斥 callback group → 同步等待 service 结果 → 处理结果又需要该 group → 两边无法推进。只换 MultiThreadedExecutor，但所有回调仍在同一个默认互斥组，通常解决不了。优先改成异步状态机；需要并行时再设计不同回调组和共享数据保护。Callback Groups 官方说明

若提示 ptrace: Operation not permitted，检查用户、Yama、容器 capability 和 seccomp。不要默认关掉整机安全限制。Linux Docker 中可在专用调试容器增加 --cap-add=SYS_PTRACE；仅在仍受 seccomp 阻止且已理解范围时增加 --security-opt seccomp=unconfined。不要给日常服务无条件加 --privileged。

真实格式会随版本变化，以下是手工简化的教学示意：

时间戳是事件发生时间；vpid/vtid 区分进程和线程，callback 是进程内回调对象标识，不是 topic 名。字段是否出现取决于事件和采集 context。地址不能跨进程或跨次运行当成同一个对象使用。

这组数字可以计算：

  • 第一次回调的墙钟持续时间：10.0804 - 10.0000 = 80.4 ms。
  • 两次开始之间的间隔：10.1001 - 10.0000 = 100.1 ms。
  • 回调结束后到下一次开始：19.7 ms，但这不是“调度延迟”。

若没有记录预期就绪／截止时间，就不能凭两个回调边界算出 Executor 的排队延迟。若没有关联某条消息的发送与处理，也不能把这 80.4 ms 称为端到端延迟。

分析时必须按进程、线程、回调标识及事件顺序正确配对，不能把整个文件里相邻两行机械相减；嵌套或可重入回调尤其需要处理。检查开始／结束是否成对，有无 discarded/lost events 提示，采集是否在回调中间结束，再计算统计量。

有事件但关联不出节点 是否漏了初始化事件；是否混了进程或不同运行的地址
Python 节点信息不完整 Humble 的核心分析主要围绕 rclcpp 埋点，不要假定 rclpy 完全相同
容器中 session / shared memory 异常 先在同一容器、同一用户运行 tracer 与节点，检查 session daemon 和 /dev/shm
提示丢事件 缩小范围／缩短窗口，评估缓冲区和磁盘开销，重采后再做结论

Docker Desktop 的 Linux 内核属于虚拟机。容器用户态跟踪可用于理解 ROS 回调，但不能把它当成 macOS 宿主的完整调度轨迹；内核 tracing 是否可用要另行确认。无需为了入门用户态 tracing 直接安装 DKMS 或改宿主内核。

九、按这三次练习学下来

第一次：找准异常位置。 构建示例，跑 normal 建立基线，再用 catch throw 跑 crash。独立写下“哪个回调、第几次、哪个容器、下标是多少”，而不是只抄整个 backtrace。改正访问逻辑后重新构建、重跑相同输入。

第二次：识别慢回调。 采 normal 与 slow 两份 trace，分别检查事件完整性、回调标识和耗时。用时间差解释 80 ms，用 CPU 观察解释为什么“慢”不一定“忙”。再把 sleep 改成 150 ms，预测它超过 100 ms 周期后开始间隔会怎样变化，然后实测；不要假定错过的 timer 会无限补发。

第三次：迁移到自己的节点。 选择一个已知故障，先保存命令、参数、版本和输入，只启用能回答当前问题的工具。修改后比较同一条件下的错误次数、回调耗时分布或吞吐，补一个能防止复发的测试。

每次最终留下一张“证据卡”：现象 → 复现条件 → 最小证据 → 原因 → 修改 → 相同条件复测。例如“日志停了”只是现象；“线程 A 在互斥组内等 future，完成回调需要同组，重复复现且改为异步后恢复”才形成可审核的原因链。
