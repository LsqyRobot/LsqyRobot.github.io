1. 制品管理究竟管理什么

1.1 用一个实际场景理解

我写了 mymath，另一个机器人项目需要它。把 libmymath.a 发给对方还不够，对方还需要知道：

  • 哪些头文件与它对应，用什么名称链接。
  • 它面向 Linux、Windows 还是其他系统，是什么 CPU 架构。
  • 编译器、C++ 标准库 ABI、Debug/Release、静态/动态选项是什么。
  • 它依赖哪些库，依赖又对应哪些版本和配置。
  • 这个二进制来自哪份源码、哪份配方，是否经过测试。
  • 有没有权利使用和重新分发它。

Conan 将这些问题组织成配方、依赖图、二进制包和仓库操作，但不会替你证明所有 ABI 假设都正确。配方建模漏了一项，工具也可能把本来不兼容的包视为同一种配置。官方二进制模型

1.2 各种工具的边界

工具／产物 主要负责 不直接替代什么
Git 仓库 配方、源代码、配置与变更历史 二进制矩阵、运行环境验证
CMake / Ninja 生成与执行编译、链接、安装规则 远程制品权限和依赖版本发布
Conan 解析 C/C++ 依赖，构建／获取适配配置的包 操作系统镜像、内核与板级驱动
Artifactory 等 Conan remote 存储与分发配方、二进制、相关元数据 替用户设计 package ID
Docker 镜像 固化应用或构建工具的用户空间环境 自动解决目标板 SDK / ABI 差异
Yocto / BitBake 构建目标 BSP、系统软件包、rootfs、SDK 自动将任意 Conan 二进制变为适配板卡的系统包

因此，制品库不只是一个网盘；Conan 缓存也不等于产品部署目录。

1.3 把生产端和消费端串起来

这里有两次“安装”：CMake 的 install 将库文件放进包暂存目录；conan install 解析并取得依赖、生成构建环境。两者都不等于把完整程序部署到开发板的 /usr。

2. 一个 Conan 制品的完整身份

2.1 五层身份，不只 name/version

字段 回答的问题 容易误会的地方
name/version 哪个逻辑组件、哪个发布版本？ 相同版本号不保证源码与配方从未改变
可选 user/channel 配方引用的额外命名空间 stable 只是字符串，不自动表示已审核或有权限隔离
RREV（recipe revision） 哪次配方／导出源码修订？ 不天然等于 Git commit；外部下载源码还需单独固定
package ID 按所建模的 settings/options/依赖等区分哪种二进制？ 不是包文件内容的 SHA，也不读取编译器真实能力
PREV（package revision） 这份包目录内容的哪个修订？ 相同 RREV 与 package ID 重新构建，仍可能因非确定性产生不同 PREV

默认内容哈希模式下，配方和导出源码的变化会影响 RREV；source() 从外部下载的源码应使用不可变 commit、固定归档及校验值，不要把浮动分支内容藏在不变的 recipe revision 后面。PREV 标识包内容，而不是“这个版本更高级”。官方 revisions 说明

2.2 三个变化，分别看什么

操作 通常先观察的字段 前提
改已导出的 mymath.cpp，版本号仍是 1.0 RREV 变化 使用默认内容哈希模式，文件确实在导出集合中
同一配方改成 Debug 或 shared=True package ID 变化 配方保留这些配置进入身份计算
同一 RREV、同一配置重新编译 PREV 可能变化，也可能相同 取决于生成内容是否相同，不应伪造“必定变化”的实验结论

RREV 不同的时候，即使 package ID 字符串相同，它们也位于不同配方修订下面，不能视为同一完整制品。

3. 配置、ABI 与双 profile

3.1 settings、options、conf 的区别

层次 例子 应如何理解
settings os、arch、compiler、build_type 环境／二进制兼容性维度；配方声明使用哪些
options shared、fPIC、with_tools 配方公开的可选功能，消费者可以选择
conf CMake generator、工具链路径、作业数 构建行为配置；并非全部默认进入 package ID
profile 上述选择的受控集合，还可带构建环境 文件名称本身不是 ABI 保证

不要为了“复用缓存”随意删除 compiler、arch 或 build_type。例如把 ARM 库的身份写成 x86_64，不会转换机器码，只会给错误的包贴上另一个标签。

同样，-s:h compiler.version=11 只是声明配置，不负责安装或切换 GCC 11。必须使实际调用的编译器、参数和 sysroot 与声明一致。

3.2 build 不是 Debug，host 也不是运行 Conan 的机器

3.3 profile detect 是起点，不是团队配置规范

conan profile detect 适合给空白教学环境生成初始配置。它不会知道团队采用哪个 Yocto SDK、哪个标准库 ABI、哪个板卡镜像。

实验脚本在独立 CONAN_HOME 中生成 profile；不覆盖你已有的默认配置。正式工程应审查并版本管理 profile、settings 扩展和关键 conf，记录真正使用的编译器版本。对于 SDK，后面的 交叉编译节 还会说明为什么路径不同未必能阻止误用缓存。

4. 配方生命周期：每个方法各管一件事

4.1 先分清描述阶段和执行阶段

入口 主要职责 不宜做的事
类属性、config_options() 定义元信息与目标平台可用选项 在此下载／编译工程
configure() 按配置移除不适用选项、整理逻辑 偷偷将不兼容配置伪装成兼容
requirements() 声明库／运行依赖 用手工拷库掩盖依赖关系
build_requirements() 声明构建工具、测试所需依赖 混淆 build 与 host 工具
validate() 拒绝不支持的标准、编译器、组合 将校验推迟到难懂的链接失败
layout() 定义 source/build/generators 等位置 在其他方法中手猜缓存路径
source() / exports_sources 获取源码／导出本地源码 使用无法追溯的浮动下载物
generate() 生成 toolchain、依赖查找、环境文件 认为生成成功就已完成编译
build() 调用真实构建系统 将所有缓存操作塞到配方里
package() 将应交付文件装入 package folder 打包整棵 build tree 和临时缓存
package_info() 向消费者声明头文件、库、组件等接口 写死本机绝对缓存路径

这张表是职责速查，不是对所有命令都严格相同的一条执行顺序。消费已有二进制时不会再执行它的 build()；本地开发命令、缓存构建和下载消费走的路径也不同。官方创建配方教程

4.2 export、create、install、build 不等价

命令 主要作用
conan export 导出配方及其声明的导出内容；不代表已经有二进制
conan create 在缓存流程中创建包，并按配置执行 test_package
conan install 解析依赖、取得或按策略构建依赖、生成消费环境
conan build 使用消费／开发工作区的配方执行本地构建
conan export-pkg 将按约定准备的预编译产物打包入缓存；不是 ABI 检测器
conan upload 发布选中的配方／二进制；不替代测试与权限审批

exports_sources 控制源码如何进入构建，不决定最终包包含哪些文件；最终交付由 package() 和 CMake 安装规则共同决定。打包时也应带上适用许可证，不能仅写一个 license="MIT" 就当作处理完了。

6. 真正从另一项目消费制品

6.1 CMakeDeps 与 CMakeToolchain 各做什么

生成器 主要作用 典型问题
CMakeDeps 将依赖接口转换成 CMake 可查找的配置与 targets find_package 找不到包、target 名不匹配
CMakeToolchain 将构建配置转成 CMake toolchain／presets 等 编译器、架构、标准、sysroot、构建目录不一致
VirtualRunEnv 提供运行依赖需要的环境 链接成功后仍找不到共享库或工具

7. Lockfile：锁住依赖选择，不锁住整个世界

7.1 固定版本号为什么还不够

requires="mymath/1.0" 固定逻辑版本，但同一版本还可能有新的 recipe revision。范围依赖 mymath/[>=1.0 <2.0] 更会受到可用新版本影响。

Conan 2 的 lockfile 记录解析出的依赖版本与配方修订。它不锁定 package ID / PREV，也不完整记录构建 profile、工具链、操作系统镜像和所有源码输入。不能把它当成“整套构建环境压缩包”。官方 lockfile 教程

7.4 升级锁也需要审查

正式更新时保留旧 lockfile，通过明确的解析策略生成候选新锁，比较依赖图并执行测试，再一起提交。不要为了让 CI 通过就删除锁，或默认加 --lockfile-partial。

条件依赖也有影响：一份只解析过 Linux 配置的锁，不一定包含 Windows 专属依赖。团队应覆盖实际矩阵并按需要合并锁。要追溯到已经发布的具体二进制，还应记录完整制品引用／PackageList、profile 与工具链信息，不能只保存 conan.lock。

8. 团队制品库：发布什么，比上传命令更重要

8.1 本地缓存、团队库和 ConanCenter

位置 使用方式 边界
本地 Conan cache 开发、构建、消费缓存 不是团队权威发布源，不直接编辑缓存内部结构
团队 remote 由服务器管理账号、读写权限和包内容 URL 与支持的 Conan 版本由管理员确认
ConanCenter 获取公共包；贡献配方向 conan-center-index 提 PR 不是给任意客户端直接 upload 的个人空间

ConanCenter 已转向 center2.conan.io；旧 center.conan.io 已冻结更新。应检查当前客户端的 conan remote list，不要从旧笔记照搬旧地址。ConanCenter 官方说明

Artifactory 是一种可选后端，Nexus 也需要按实际版本、授权与仓库类型核对 Conan 2 支持，不能把旧文中的占位 URL 当成可用服务器。Nexus 3.76.0 的官方发布说明记录了 Conan 2 支持的引入；具体使用限制以所部署服务器的文档为准。Nexus 发布说明、Conan 仓库配置

9. 原来的几种打包场景，怎样用 2.x 正确理解

9.1 静态库、动态库与运行时依赖

类型 应交付的典型内容 特别关注
静态库 头文件、.a/.lib、接口元数据、许可证 链接依赖传递、PIC、编译器与 ABI
动态库 头文件、共享库，Windows 通常还需 import library DLL 导出、SONAME、RPATH、运行库与符号版本
可执行工具 可执行文件、必需资源与运行依赖 是 build 机工具还是 host 机应用
混合包 库、可选工具、各自依赖 是否需要拆包／components，选项是否完整
Header-only 头文件、必要配置与许可证 不一定需要多种二进制，但仍需验证使用方标准与依赖

链接成功只是第一步。共享库在目标机运行时还要被动态加载器找到；Linux 的 libstdc++ 符号版本、目标 glibc、Windows CRT、RPATH 都不应被“Conan install 成功”掩盖。

需要运行环境时，可在配方中使用 VirtualRunEnv，执行测试时用 self.run(..., env="conanrun")。它负责开发／测试环境，不等于最终产品安装器；部署时仍要设计目标目录、运行库和服务配置。VirtualRunEnv

9.2 可执行工具：requires 还是 tool_requires

编译时运行的代码生成器，应放进 build context；部署到机器人上的命令行程序则是 host 产物。它们有时来自同一个源码仓库，但运行机器不同。

旧文“可执行文件通常只要 os/arch，不用 compiler/build_type”的表述过于宽泛。若动态依赖特定 C++ runtime、glibc 或特定编译选项，就仍需准确建模。减少 settings 之前，先证明被合并的变体确实兼容。

Conan 2 的目录接口是 cpp_info.bindirs；需要额外运行环境时使用 runenv_info / 对应环境生成器，不用旧式 env_info。仅声明一个 bin 路径也不会自动让任意 shell 都拥有正确 PATH。

9.3 预编译库不是按文件后缀分类就够了

使用 conan export-pkg 或自定义打包 recipe 接收供应商二进制前，先整理：

核对项 为什么重要
来源、版本、SHA-256、许可证 确认拿到的文件和分发权限
ELF / PE / Mach-O 架构 后缀为 .so 不代表就是目标 ARM 库
编译器／标准库 ABI／系统 baseline 同 CPU 架构不保证链接与运行兼容
所需共享库、插件、资源、固件 单个库文件未必构成完整运行环境
Debug/Release、shared/static、PIC 等 不能为所有配置复用一份不匹配二进制
消费者编译／链接／运行测试 包装成功只说明文件进入缓存

必须拒绝不受支持的配置，不能让一个 Linux x86_64 的预编译目录在 arch=armv8 下被无条件复制并发布。

9.4 Header-only：去掉无关二进制维度，不去掉验证

真正与平台无关的纯头文件库可使用 package_type="header-library"，不声明不必要的二进制 settings，并把无意义的 cpp_info.libdirs/bindirs 设为空。

如果为了测试而声明了编译器配置，package_id() 可以按实际内容去除不影响交付文件的维度；但不能不加判断地 self.info.clear()。生成的配置头、条件依赖或嵌入平台差异时，所谓“头文件库”也未必完全相同。

需要 C++17 时，使用配方验证与 CMake 的 compile features 表达要求，不向所有消费者盲目拼接 -std=c++17。官方 Header-only 模式

9.5 混合包、components 与条件依赖

当一个包同时有 core 库、插件和命令行工具时：

  • options 显式控制可选功能，并传到真实构建系统。
  • requirements() 根据实际选项声明依赖；不要声明后却不链接，也不要链接了却不声明。
  • 需要独立消费接口时，使用 cpp_info.components 描述各组件及依赖，避免消费者被迫链接全部内容。
  • cpp_info.system_libs 是明确声明已知的系统链接库，不是“自动检测系统依赖”。
  • 仅当需求确实如此才声明 pthread/dl/m 等，不能对所有平台无条件添加一串库。

这些是扩展设计入口；本文最小实验只用单库，没有伪装成已测所有 components 和平台矩阵。

  2. sysroot、CPU flags、标准库 ABI、链接器选项是否保留。
  3. find_package 与 pkg-config 是否误选宿主库。
  4. Conan 的 libcxx／flags／安装路径生成块是否与 SDK 冲突。
  5. 最终 verbose 编译命令与 CMakeCache.txt 是否一致。

10.4 双 profile 不会自动隔离 shell 环境

Yocto 环境脚本可能将编译器、CPU flags 和 sysroot 一起放入 CC/CXX。不要把完整命令字符串当成 tools.build:compiler_executables 里的“可执行文件路径”。

更可控的做法，是将核对后的 SDK 环境放入 host profile 的 [buildenv]，覆盖 SDK 所需的编译器、flags、PATH、sysroot、pkg-config 等内容。构建本机工具的 build profile 则保持原生环境。

如果选择先 source environment-setup-* 再运行 Conan，要意识到：进程继承的全局环境不会因写了 -pr:b / -pr:h 就自动消失，可能污染本机工具。清理／覆盖哪些变量应按实际 SDK 审查，不给出一个随意清空所有环境的脚本。Conan profile 环境配置

11. 从开发缓存到可追溯交付

11.1 CI 需要固定的不只有 conan.lock

记录项 用途
源码与 recipe commit、干净工作树／补丁 对应真正构建的输入
Conan 版本、Python 环境、CMake、编译器 定义工具行为，避免客户端升级导致差异
build / host profiles、settings 扩展、关键 conf 固定二进制配置及 SDK 边界
lockfile 固定已解析依赖版本／RREV
remote 地址与优先级策略 防止同名包来自意外来源
RREV、package ID、PREV、发布 PackageList 追溯具体交付制品
Docker 基线、SDK 摘要、sysroot 契约 防止相同名字对应不同工具链
构建、test_package、消费、运行日志 证明验证实际发生

这是本文的工程检查表，不是 Conan 通过一条命令自动保证的属性。哈希能说明内容一致，不能单独证明发布者可信。

11.2 缓存可以加速，但不是共享工作目录

Conan 2.15 的 package cache 不支持并发访问；并行 CI job 应使用各自独立的 CONAN_HOME，复用通过受控的缓存保存／恢复或远端下载实现。不能仅仅规定“不同时手改文件”，却让多个 Conan 进程并发操作同一缓存。2.15 官方说明

不要遍历缓存内部目录拷走看起来像 lib 的文件，并把这些路径写进构建脚本。

conan cache save/restore 可用于按工具支持的方式搬运缓存内容；它们不是通用安装器，也不是跨客户端版本、跨 ABI 的兼容性承诺。离线工作流还需要保证依赖图中的配方和对应二进制完整、profile 一致，并在断网环境实测。cache 命令

11.3 --build=missing 和 --build=never 分别适合什么

策略 合适的阶段 风险／检查
--build=missing 受控开发或专门的制品生产任务 可能拉源码重建，带来时间、许可证、工具链差异
--build=never 检查制品矩阵完整性、受控制品消费 缺包就失败，需要先补对应配置
强制重建指定包 修改配方或排查构建输入 避免每次重建全部依赖产生无用修订

“missing”不等于“重新验证所有已经命中的制品”。如果 SDK 差异没有进入兼容性模型，重用错误二进制时不会因为写了这个选项就自动重建。

11.4 最终部署不直接带走 Conan cache

应用交付应有明确的目录和清单，例如程序、共享库、许可证、配置、服务文件与版本记录。选择原生包、容器或 Yocto recipe 取决于项目的系统集成方式；不要把整个 CONAN_HOME 当作软件安装包。

对于机器人或嵌入式应用，还应记录驱动／固件需求、运行用户、设备权限、日志、watchdog、失败退出行为与回滚方式。构建成功解决的是“得到产物”，不是“设备上的行为已经可靠”。

14.1 自动实验检查什么

  1. 创建 mymath/1.0 的 Release 与 Debug 包，执行各自的 test_package。
  2. 比较真实 JSON：同一 RREV、不同 package ID。
  3. 创建 consumer 的 lockfile，再创建 mymath/1.1。

  5. 改动导出源码并再创建 1.0，检查 RREV 改变，旧锁仍保持原修订。

  7. 请求没有生成的 RelWithDebInfo，断言出现缺失二进制错误。

失败实验也必须检查具体错误，而不是把任何非零退出都叫作“符合预期”。2026-09-09 已在 Docker 内的 Linux ARM64 原生环境完成 24 项自动检查：Conan 2.15.0、GCC 11.4.0、CMake 3.22.1。包括 4 次创建与包消费测试、3 次消费者编译执行，以及预期缺失二进制的反例。

可查 真实验证摘要 与 完整命令日志。摘要记录源码、工具配置和日志哈希；可据此判断下载记录是否对应这版脚本。aarch64 原生编译不是 x86 → ARM 交叉编译，更不是高通板上实测。

此外，在另一份空白缓存中按第 5—7 节的手动命令独立复核，15 项检查通过：确认 conan build 的输出路径与运行结果、锁定前后版本选择、预期的缺失二进制，以及 Linux shared=True 的包消费测试。远程发布相关只检查 Conan 2.15.0 的 upload --help 参数，没有执行上传。见 手动流程复核摘要 与 命令日志。

两组实验的 profile 有一个有意保留的差异：自动 runner 显式指定 compiler.cppstd=17，手动流程使用检测得到的 gnu17。这也会影响 package ID，因此应比较同组实验中的制品身份，不要机械地对照两份日志的 ID。复跑入口、证据校验方式和完整 Dockerfile 都在前面的源码下载包内。

14.2 尚未覆盖的范围

这份最小实验不代表已经完成远程 Artifactory/Nexus 发布、Windows/macOS 原生库矩阵、高通 SDK 交叉编译或真机部署；也不代表产品级许可证、签名、漏洞和性能审核。

扩展到自己的项目时，先替换最小库，然后一次增加一个变量：第三方依赖 → shared → 工具包 → CI remote → SDK 交叉目标 → 板上验收。每一步保留输入、结果和失败证据。

15. 从教学实验到自己的常用制品架

前面的 mymath 用于理解机制；实际开发还需要一组经过统一配置和消费验证的常用库。现在另建 docker/conan-artifacts/：不修改原教学实验，也不直接替换现有机器人服务里的系统库。

构建工具镜像与首次获取源码需要联网；verify 在新建的断网容器与空白 Conan 缓存中恢复，不允许从旧缓存或远端悄悄补齐。若该架构还没有审核锁，create 会停止，只有显式 --bootstrap 才进行第一次依赖解析；解析后还要审查并固化锁，不把未来每次运行都变成一次隐式升级。

15.3 真正验收的是“恢复以后能用”

消费程序会真的做 Eigen 求解、日志输出、JSON/YAML 往返和两种 XML 解析，而不是只检查头文件存在。恢复前后比较完整 RREV/package ID/PREV；另用空缓存和没有准备过的 SDK 基线做反例。

manifest.json 保存实际环境和制品哈希；verification.json 记录最新验收结果。built 只表示生产完成，passed 才表示该次离线消费通过。 对外复制或开始新项目时，先查看验证结果，不能只看 last-built。

2026-09-09 实际得到 10 个配方、18 份制品，缓存归档约 40.9 MiB；同一归档已在两个全新断网 ARM64 Linux 容器中分别通过上述六组检查。每个配置的消费程序包含 5 项 GTest。工具镜像也已保存并校验，本机重复恢复通过不代表第二台机器或高通目标板已经验证。

15.4 哪些依赖仍然不能混在一起

profile 用 tools.info.package_id:confs 把自定义基线标识纳入包身份，但它不会自动识别 SDK。换 sysroot、libc、编译器契约或目标板时，必须维护新的基线和实际验证。

第三方库采用静态链接，不代表程序完全静态：glibc、libstdc++ 等系统运行库仍须匹配。迁移时同时带走制品 bundle 和构建工具镜像；镜像可用 ./bin/site.sh artifacts-image-save 保存。仅复制 Conan 缓存不等于复制了编译器和目标运行系统。

Pinocchio、Boost/OpenCV、ONNX Runtime、ROS2、OCS2 与高通 SDK 后续按实际功能和平台组合逐批加入；现有 ROS/仿真镜像保持原版本，待替换依赖时还需跑各项目原有回归。当前制品架是本地使用，不是已经上线的团队制品服务器，也没有执行远程上传。

缓存保存/恢复的边界可查 Conan 2.15 官方手册第 6.6 节。固定 2.15.0 没有新版 cache save --no-source 参数，本工具没有使用它。
