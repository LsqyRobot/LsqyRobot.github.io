ROS 2 rqt 实战：通信图、数值曲线、日志与图像

文章目录

启动了驱动和控制器，机器人却没有按预期运动：先看谁在发消息，再看数值有没有变化，最后对照日志。rqt 适合把这些观察放在同一个调试工作台里；它不是仿真器，也不替代命令行。

本文以 Ubuntu 22.04 + ROS 2 Humble 为基线，介绍最常用的 Graph、Plot、Console 和 Image View，并用 turtlesim 串起一条不连接真机的排查流程。核对日期：2026-10-12。空间位置、机器人模型与点云显示接着看 RViz 实战。

一、rqt、RViz 和仿真器分别看什么

工具 主要问题 不应据此下的结论
rqt 谁与谁通信？字段怎样变化？节点报了什么？ 图上有连线，不等于数据有效或控制闭环正确
RViz 数据在哪个坐标系？模型、路径、点云是否对齐？ 画面正常，不等于接触、力矩或动力学正确
Gazebo 等仿真器 给定模型和输入，系统怎样演化？ 仿真能跑，不等于真机参数和时延一致

rqt 是可加载插件的 Qt 界面。可以在主窗口中组合多个插件，也可以单独启动某一个。在自己的工作流里，我更倾向于先问一个具体问题，再打开对应插件，避免所有面板同时挤满屏幕。

迁移到机器人控制调试时，比较有用的组合是“指令—反馈—误差”：

观察对象 能帮助发现什么 对齐前提
目标与实测关节位置 跟踪延迟、偏差、振荡 同一关节、同一单位、相同零位约定
速度指令与里程计速度 限幅、死区、响应慢 坐标系和速度分量一致
力矩指令与反馈 饱和、符号反向、异常尖峰 分清电流、估计力矩和真实传感器力矩

对于 sensor_msgs/msg/JointState，position[0] 是数组第一个元素，不自动等于“左前髋关节”。先查看 name 与数组顺序，再决定字段；数组顺序若会变化，应先在调试节点里按名字重排或发布命名明确的标量话题。

Plot 的 GUI 刷新、缓存与绘图库都有开销，不能把屏幕上每个像素当成实时控制周期的精确测量。需要查毫秒级延迟或抖动时，记录原始消息及时间戳，或使用 tracing；ros2 topic hz 测到的也是该订阅端观察到的接收频率，不能直接当成发布线程的精确周期。参见 ROS 2 排障：GDB、日志与 Tracing。

曲线为空时按顺序看：话题有没有消息 → 字段是不是数值 → 是否暂停绘图 → 时间范围是否合适 → 订阅 QoS 是否匹配。字段路径与插件支持范围可对照 rqt_plot 项目。

六、用 Image View 先确认图像流

当相机算法没有输出时，先用 Image View 选择实际图像话题，确认是否持续出图、是否黑屏、方向是否正常。若想选择压缩 transport，发送端和查看端都要具备对应的 image_transport 插件；它不是把任意消息强行变成图像。

不要仅凭显示颜色判断深度单位。深度图的编码、驱动约定与可视化归一化都影响观感；要同时检查消息的 encoding 和上游说明。看得到彩色图，也不等于相机内参、深度对齐和外参正确。

只想看一帧图像，用 Image View；想确认相机与机器人或点云的空间关系，转到 RViz 的 Camera/PointCloud2/TF 显示。插件实现与 transport 支持见 rqt_image_view 项目。

八、在四足机器人项目里怎么搭配

例如“发了速度指令，但四足没有向前走”，可以沿着信息流检查：

  1. 用 Graph 确认命令发到了正确命名空间下的控制节点。
  2. 用 Plot 对比输入速度、控制器实际接收值与里程计反馈，注意坐标系。
  3. 用 Console 对照模式切换、使能、限幅与安全状态的日志。
  4. 用 RViz 查看机身朝向、足端位置、里程计和传感器坐标是否一致。

rqt 也有服务调用等能改变系统状态的插件；对真机不要随意点击使能、模式切换或运动相关服务。本文的小海龟例子与硬件无关，结束后在各启动终端按 Ctrl+C。

本文已核对本机 Humble 包入口及 Plot、rqt 的命令行参数；不把这些检查等同于实际机器人或全部 GUI 场景的验收。
