Ubuntu 及 Ros 配置

文章目录

前言

配置机器人开发机，需要依次确认四件事：操作系统与 ROS 能否配对，软件包能否可靠安装，当前终端是否找到正确的工作区，节点能否访问网络与硬件。 安装命令执行完，只完成了其中一部分。

这篇笔记最初记录 Ubuntu 20.04、VirtualBox 和 ROS 1 Noetic。现在按截至 2026-10-13 的官方资料更新，主流程采用 Ubuntu 24.04 + ROS 2 Jazzy；使用本站 Humble Docker 环境的项目，则保持 Ubuntu 22.04 + Humble。命令默认在 Ubuntu 的 Bash 中运行，Zsh 的差异单独说明。

Ubuntu 与 ROS 版本配对

以下组合适合本篇的 Ubuntu 二进制安装流程。amd64 对应常见 x86-64 PC，arm64 对应 64 位 ARM；Ubuntu 支持某个架构，并不代表所有机器人驱动都已为该架构发布。

Ubuntu ROS 版本 Ubuntu 标准安全维护至 ROS 支持至 使用场景
26.04 LTS，Resolute ROS 2 Lyrical 2031 年 5 月 2031 年 5 月 新平台；先确认设备驱动和 SDK 已适配
24.04 LTS，Noble ROS 2 Jazzy 2029 年 5 月 2029 年 5 月 本文主流程，依赖适配此组合的开发项目
22.04 LTS，Jammy ROS 2 Humble 2027 年 5 月 2027 年 5 月 现有项目、厂商 SDK 与本站 Humble 环境
20.04 LTS，Focal ROS 1 Noetic 已于 2025 年 5 月结束 已于 2025-05-31 结束 历史项目的隔离维护与迁移

依据 Ubuntu 生命周期、ROS 官方发行版列表和 Noetic EOL 公告。Ubuntu Pro 的扩展维护与 ROS 发行版的维护是不同承诺，操作系统仍有扩展支持，不等于 Noetic 仍在官方维护期。

Jazzy 的 Ubuntu deb 包面向 24.04，Humble 面向 22.04；Lyrical 的 Ubuntu 26.04 amd64/arm64 是 Tier 1，而 24.04 是需要源码构建的 Tier 3。不要给 24.04 添加 Jammy 源来装 Humble，也不要把 26.04 的 Lyrical 包装进 24.04。配对见 Jazzy 安装说明、Humble 安装说明和 Lyrical 平台表。

先列出项目需要的 ROS 包、SDK 和内核驱动，再决定系统版本。Rolling 持续变化，适合测试新功能；长期项目应固定发行版。跨 ROS 发行版通信也不保证兼容，联调时尽量统一版本。

宿主机、虚拟机与 Docker

方式 适合的工作 提前确认的边界
Ubuntu 原生安装 USB、GPU 可视化、机器人实机联调 设备驱动、双系统备份、磁盘容量
Ubuntu 虚拟机 Windows/macOS 上学习 CLI、编译普通工作区 CPU 架构、USB 直通、3D 加速、虚拟网卡模式
Linux Docker 容器 固定依赖、自动构建、多项目隔离 网络命名空间、设备映射、用户 ID、持久化目录

虚拟机用于本机 talker/listener 时，NAT 通常足够；需要与局域网机器人发现彼此时，桥接更容易保持直观的拓扑，但仍取决于宿主策略和多播支持。相机和串口接入后，先在虚拟机中确认设备存在，宿主机能看到设备不代表虚拟机也能访问。

容器有自己的文件系统与环境。宿主机执行过 source /opt/ros/... 不会自动配置容器；源码、日志和 bag 需要挂载或明确导出。原生 Linux 的 host 网络也不能直接等同于 Docker Desktop 的宿主网络行为，跨容器发现应按运行平台核验。Docker host 网络文档解释了平台边界。

本站已有 Docker 项目优先遵循对应的 Dockerfile、Compose 和 README。不要在宿主机再安装一套相同依赖去修补容器中的缺包。

先读取 APT 软件源

Ubuntu 源提供基础系统包，ROS 源补充 ROS 的包。读取配置与更新索引：

24.04 等系统常使用 deb822 格式的 ubuntu.sources，旧系统可能主要使用 sources.list。替换镜像时只改服务器地址，保留发行版代号、updates/security 条目与签名设置。不能复制另一 Ubuntu 版本的源，也不要为解决签名报错关闭校验。参见 Ubuntu 软件包管理文档。

apt update 更新索引，不会升级全部软件。成功信号是没有签名、Release 文件、DNS 等错误；Ign 本身不一定失败，要结合最后的警告判断。镜像慢先确认网络与 DNS，再考虑换镜像，避免同时改变多个条件。

安装基础开发工具

universe 提供许多开发依赖；编译器与 CMake 供 C++ 包使用，Git 管理源码，venv 供独立 Python 工具隔离依赖，psmisc 提供后面的锁诊断工具。审阅升级列表并按提示重启。全新 22.04 应先更新 systemd/udev 等基础包，再安装 Humble，详见 官方安装提示。

不要用 sudo pip install 覆盖系统 Python 的 ROS 依赖。venv 是否能导入 rclpy，取决于系统包可见性、Python 版本和扩展模块 ABI；ROS 节点先使用发行版自带 Python 验证。

dpkg frontend lock：先找到持锁进程

APT 用锁防止多个安装操作同时修改数据库。开机自动更新、软件商店或另一个安装终端都可能持锁。删除锁文件不能停止正在运行的包管理器，还可能破坏并发保护。 原因见 Debian dpkg 官方 FAQ。

进程正常下载或配置时，等待完成并关闭重复安装界面。若确实卡死，先查日志与磁盘，再有针对性地停止对应服务或进程并确认退出；不要直接 kill -9 全部 apt/dpkg。

ROS_TARGET 是安装阶段的变量，不等于加载环境后设置的 ROS_DISTRO。输出应与项目一致；接下来的安装代码块在同一个终端运行。

使用官方包管理源与密钥

当前流程用 ros2-apt-source 管理源与签名配置，替代旧文的 apt-key adv。见 ROS 官方源配置与 ros-apt-source 项目。

配置记录中保存实际下载版本。下载失败就停在该步骤，不要继续安装旧的临时文件。已有 ROS 源的机器先查重复 URI 或冲突的 Signed-By，按官方迁移说明整理旧条目；不必再手写一份重复的 ROS 源。

选择 Desktop 或 ROS Base

apt-cache policy 应有候选版本；没有候选时先查代号、架构与索引更新结果。Desktop 带 RViz、示例等，适合开发机；无图形设备可换成 ros-${ROS_TARGET}-ros-base，需要示例时另装 ros-${ROS_TARGET}-demo-nodes-cpp 和 ros-${ROS_TARGET}-demo-nodes-py。

Jazzy 安装 ros-dev-tools 出现依赖版本冲突时，查 ubuntu.sources 是否包含 noble-updates/noble-backports 和单独的 noble-security 条目。不要把全部 Suites 填到安全更新专用服务器。Jazzy 安装页给出了该检查点。

Noetic 仅用于历史项目维护

旧文的 ros-noetic-desktop-full 属于 ROS 1，主要对应 20.04。保留隔离的旧环境、源码与包版本、bag 数据，并制定迁移计划。Noetic 的 roscore/catkin/rostopic 与 ROS 2 的 ros2/colcon 是不同工具链；不要把两套 setup 同时写入同一个终端启动文件。

underlay、overlay 与工作区

理解包的搜索顺序

/opt/ros/jazzy 是系统安装的 underlay，~/ros2_ws 是开发 overlay。加载 overlay 后，同名包可能优先从 overlay 找到；系统安装了某个包，不代表当前运行的是系统包。

构建终端加载所需 underlay；运行终端再加载 overlay。切换发行版、底层依赖或构建布局后，在新终端重建环境，避免旧路径参与解析。见 官方工作区教程。

通信：环境、发现、数据三层排查

Domain ID 与当前环境

在每个参与通信的终端或容器中检查：

DDS 的 ROS_DOMAIN_ID 划分逻辑通信域，不同 Domain 的节点通常互相看不到。同一项目统一一个低位值，例如 export ROS_DOMAIN_ID=10，再重启节点。范围与进程数量、UDP 端口有关，不能无限增加；见 Domain ID 说明。

多机还要查 ROS_LOCALHOST_ONLY：Humble 中为 1 时限制在本机。Jazzy/Lyrical 可使用 ROS_AUTOMATIC_DISCOVERY_RANGE 等发现设置，按项目选择 SUBNET/LOCALHOST；先检查旧设置，避免遗留矛盾配置。这些发现范围变量不适用于 rmw_zenoh，它需要自己的路由配置。见 官方发现范围说明。

发现节点与传输数据分别检查

重启 CLI daemon 不会重启节点或修复 QoS，应用节点需要在新环境中重新启动。先用同 ROS 版本、同 RMW 建立最小链路，避免同时引入跨发行版与跨中间件变量。

多播可用一台的 ros2 multicast receive 与另一台的 ros2 multicast send 检查。收到报文仅说明这条多播路径可达，不代表全部 DDS 端口已放行。单机正常、多机失败时，查路由、网卡、VPN、NAT 和防火墙；用 sudo ufw status verbose 读取状态，按实际 DDS 配置设置允许范围，不把关闭防火墙作为默认方案。

有话题但 echo 没消息

传感器常用 best-effort，订阅者请求 reliable 时可能不匹配。上面的 echo 用于排查这一假设，前提是已确认类型与端点 QoS。hz 是当前订阅者观察到的接收频率，受网络、CPU 与 QoS 影响，不一定等于硬件采样率。

reliability、durability、history/depth 要结合用途决定，不能为了看到消息全部改成 best-effort。继续看 ROS2 QoS 配置策略和 rqt 通信图与曲线。

磁盘、日志与 bag

df -h 查容量，df -i 查 inode；大量小文件也会在还有容量时耗尽 inode。du 查具体目录。ROS 运行日志常在 ~/.ros/log，colcon 日志在工作区 log，bag 在录制时选择的输出目录。见 ROS 日志说明。

空间不足先停止写入任务，保存需复现的日志与 bag，再有选择地归档清理。APT 下载缓存可用 sudo apt clean 清理；journal 按容量策略管理；工作区 src 是源码，不能和可再生成的构建目录一起删。容器空间另用 docker system df 检查，不把清理全部 Docker 数据作为常规操作。

sudo、自动登录与桌面偏好

sudo 保留默认授权方式

旧文把全体 sudo 组改为 NOPASSWD:ALL，会让组内所有用户无密码执行任意管理员命令。日常开发保留默认策略，频繁执行一组管理命令时可先 sudo -v 更新凭据缓存。

确需免密自动化时，把规则限定到专用用户、固定程序与所需参数，用 sudo visudo -f /etc/sudoers.d/robot-task 编辑，再用 sudo visudo -c 验证。脚本应由管理员拥有、普通用户不可修改；只限制路径却允许用户改脚本内容，并没有限制权限。具体语法见 Ubuntu sudoers 手册。

自动登录改变登录体验

单人虚拟机可在“设置 → 用户”中解锁后启用自动登录，位置随桌面版本变化。它省去进入桌面的密码，不会取消 sudo 验证，也不能代替磁盘加密；共享开发机按场景保留登录控制。见 GNOME 自动登录说明。

桌面图标先检查扩展

旧文的 org.gnome.shell.extensions.desktop-icons 仅适用于特定旧扩展。新系统可能用 Desktop Icons NG（ding），先运行 gsettings list-schemas | grep -E 'desktop-icons|ding'，再用 gsettings list-keys 对应schema 查看实际选项，或在扩展设置中关闭家目录与回收站图标。没有 schema 时不要继续套用旧命令。

保存可复现配置清单

记录至少包含 Ubuntu 版本与架构、内核、ROS 发行版、源配置包版本、项目 Git 提交、构建命令、加载顺序、RMW/Domain、设备规则与验收结果。“最新版本”要落到实际版本号，才能解释以后两台机器为什么表现不同。

人工补充：talker/listener 是否互通，项目能否从新终端构建，包 prefix 是否指向目标工作区，设备重新插入后的名字是否稳定，多机时钟与通信是否正常。导出前检查代理凭据、密钥等内容，记录只保留复现所需信息。

后续升级系统、切换 ROS 或更改驱动时，用这份记录比较差异。配置完成的标准是 能说明当前加载了哪套环境，并能用最小链路证明编译、通信和设备访问各自正常。
