ROS2 QoS 配置策略

文章目录

同一个话题，ros2 topic list 能看见，自己的回调却一直不执行；相机画面正常，但图像和 IMU 的同步回调不触发；机器人收到速度指令后，在通信断开时还沿用上一次速度——这些现象不一定是同一种问题。

QoS 要解决的是通信双方怎样交换和保留数据。它不是线程调度器，也不是控制器，更不是机器人安全机制。理解这几个边界，比背下 RELIABLE 和 BEST_EFFORT 更重要。

本文以 Ubuntu 22.04 / ROS 2 Humble 为基线，按“概念 → 配对 → 配置 → 复现 → 工程取舍”的顺序展开。API 与默认值核对到官方 Humble 分支；文中的实验给出了预期现象，尚未在本仓库的 ROS 开发镜像中完成运行验收，不能把示例当成已测量的延迟或真机安全结论。

如果接下来要把指令接到关节、电机和控制循环，可以继续阅读：ROS 2 控制系统：ros2_control、Controller Manager、Executor 与硬件接口。

1. 先建立一条完整的数据链

这张图里至少有三种“到了”：

  1. 数据到了接收端中间件。
  2. Executor 调用了订阅回调，应用拿到了消息。
  3. 应用接受并完成了消息对应的工作，例如电机真的运动到目标位置。

不能把第 1 步直接当成第 3 步。可靠通信也不能证明回调没有阻塞、控制器接受了目标，或者驱动器没有报错。Humble 的 Executor 通常通过 wait set 判断实体是否有工作，消息在被取走前仍由中间件管理；因此“节点还活着”不代表“回调及时执行”。官方 Executor 机制说明

1.1 Profile 不是整个节点的统一开关

一组 QoS 策略组成一个 profile。一个节点内的不同 publisher、subscription、service 可以有不同配置；同一个话题上的多个端点，也可能只有一部分彼此兼容。

例如定位节点可以同时使用：

  • 图像订阅：允许丢帧，优先处理新画面。
  • 地图订阅：需要晚加入时取得当前地图。
  • 定位结果发布：面向消费者分别评估可靠性和缓存。
  • 重定位服务：需要请求、应答和明确的超时处理。

所以不要问“这个节点应该用哪种 QoS”，先问“这个端点消费的是什么数据，过期后还有没有价值”。

2. 七组策略，分别约束什么

2.1 History 与 Depth：缓存数量，不是缓存时间

KEEP_LAST(N) 表示有限历史；KEEP_ALL 表示尽量保留历史，但仍受到 DDS 资源限制。depth 只在 KEEP_LAST 下表达这个数量上限。

发布侧和订阅侧有各自的缓存，并不是双方共享一个长度为 N 的队列。应用可能另外还有工作队列、message_filters 队列和算法内部窗口。

假设相机 30 Hz，算法每帧需要 80 ms，算法理想吞吐量只有约 12.5 Hz。把订阅深度从 5 调到 100，并不会让计算变快：

  • 如果逐帧处理，积压会把实时画面变成“几秒前的录像”。
  • 如果业务只需要当前目标位置，应该考虑丢弃待处理旧帧，而不是无限加缓存。
  • 如果业务是离线重建，保留全部原始帧有价值，但要通过录制、磁盘吞吐和离线计算设计保证完整性。

粗略地说，频率为 f 的稳定数据流，N 个样本覆盖的时间跨度约为 (N - 1) / f。这只是历史窗口估计，不是延迟上界；网络、调度和应用队列还会增加等待时间。

Humble 的类型定义还区分 history、depth 与其他时长策略，不能把一个 depth=10 理解成“消息 10 ms 后过期”。RMW QoS 类型定义

2.2 Reliability：需要补传，不等于业务必然完成

BEST_EFFORT 更接近“尝试发送，允许在传输条件不足时丢失”；RELIABLE 要求可靠交付机制，可能涉及确认、重传和额外等待。

原先笔记里的“RELIABLE 确保消息一定会送达”过于绝对。更准确地说：它提供中间件层的可靠性语义，不承诺在任意断网、进程崩溃、资源耗尽、消息过期等条件下，应用都能及时处理每一条消息，也不承诺业务上的 exactly-once。

对控制系统有一个很实际的区别：

前者通常需要小缓存、新鲜度和失联停机；后者更需要带请求标识的服务或 Action、执行状态与超时恢复。二者不能都靠“调成 reliable”解决。

可靠性也不等同于传输协议名称：不能写成“reliable 就是 TCP，best effort 就是 UDP”。DDS/RMW 的实现与传输选择是另一层问题。ROS 2 Humble QoS 概念

2.3 Durability：晚来的读者，要不要补历史

VOLATILE 不要求为晚加入订阅者保留旧数据；TRANSIENT_LOCAL 让仍存活的发布端保存一定历史，用于符合要求的晚加入订阅者。

需要注意四件事：

  1. 想补历史，发布端和订阅端都应配置 TRANSIENT_LOCAL，只改一边不够。
  2. 历史数量受发布侧 history/depth 等条件约束；深度 1 通常是“最新一份快照”，不是全部版本。
  3. TRANSIENT_LOCAL 不是磁盘数据库；原发布端消失后，不能指望新进程自动继承它的缓存。
  4. 不要给持续运动指令随手加持久性，否则刚启动的消费者可能把旧指令当成当前意图。

2.4 Deadline：应该多久有一次数据

Deadline 关注相邻数据更新之间允许的最大间隔。例如预计 50 Hz 更新，可以按业务允许的抖动设定 30 ms，而不是机械地把 deadline 设成恰好 20 ms。

它有两个容易混淆的层次：

  • 匹配阶段：发布端声明的 deadline 能否满足订阅端要求。
  • 运行阶段：匹配后是否出现 deadline missed 事件。

如果发布端声明 20 ms、订阅端允许 50 ms，约束可以满足；反过来发布端声明 50 ms、订阅端要求 20 ms，则不能满足。有限时长下可以记作：

Deadline 不是定时器：设置 20 ms 不会替你创建 50 Hz 的 publisher。它也不是执行期限：收到 deadline missed 事件时，并不会自动停止机器人。

2.5 Lifespan：这份消息还值不值得交付

Lifespan 关注一条样本从发布起的有效寿命。过期样本可能被中间件丢弃，而不是晚到后仍交给消费者。

这与消息 header.stamp 不同：相机图像可能采集后 150 ms 才调用 publish()。即使发布后的 lifespan 没超时，图像也早已不符合“采样到执行不超过 100 ms”的业务要求。

因此对新鲜度敏感的应用通常还需要检查：

  • 采样或指令生成时间，而不仅是 publish 时间。
  • 时间戳使用的时钟是否一致。
  • 应用自身缓存有没有再次把消息放旧。

订阅回调已经取出的消息也不会因为 lifespan 到期就从你的应用变量里自动消失。

2.6 Liveliness 与 Lease Duration：发布实体是否仍活跃

AUTOMATIC 由中间件管理活跃性；MANUAL_BY_TOPIC 用于需要应用显式维护话题活跃性的场景，例如通过 publisher API 断言活跃。Lease Duration 是允许多长时间没有满足活跃性条件。

“活着”和“产生有效结果”不是一回事。进程的通信线程仍然工作时，算法线程可能已经卡住；反过来，一个低频发布配置的节点也未必应该被判死。

可以用几类问题区分这几种机制：

问题 首先考虑什么
这一条消息已经太旧了吗？ Lifespan + 业务时间戳检查
这路数据太久没有更新了吗？ Deadline + 应用接收 watchdog
发布实体还被认为活跃吗？ Liveliness + lease duration
控制输出还能安全继续使用吗？ 控制器状态机、指令有效期、硬件保护

2.7 System Default：把决定交给当前实现

SYSTEM_DEFAULT 不等于“永远 reliable、深度永远 10”。它把相关决策留给 RMW/DDS 实现或供应商配置。时长的 DEFAULT 也不是“0 秒立即过期”；它表示未明确指定，由实现解释。

可复现实验应记录实际端点 QoS、ROS/RMW 版本及供应商配置，不只记录源码中的 preset 名称。遇到 UNKNOWN 或默认值时，也不要把静态兼容性检查返回的 warning 当成“肯定兼容”。Humble RMW profile 与兼容性检查接口

3. 发布端与订阅端怎样配对

3.1 Request vs Offered，不要求逐项相同

订阅端提出需求，发布端提供能力。影响匹配的策略需要同时满足要求。

Publisher 提供 Subscription 请求 Reliability 是否兼容
Best effort Best effort 是
Best effort Reliable 否
Reliable Best effort 是
Reliable Reliable 是

最常见的问题是传感器驱动提供 best effort，而自己使用默认 reliable 订阅。话题和消息类型都对，数据依然不会到这个订阅者。

持久性则要连“是否补历史”一起判断：

Publisher 提供 Subscription 请求 是否兼容 晚加入时的语义
Volatile Volatile 是 只期待新数据
Volatile Transient local 否 发布端不能提供所需历史
Transient local Volatile 是 不应依赖取得旧缓存
Transient local Transient local 是 可取得发布端仍保留的历史

有限 deadline 和 lease duration 的匹配方向都是“提供的间隔不大于请求允许的间隔”。发布端默认 deadline 配上订阅端明确的有限 deadline，不要想当然地认为能匹配。Liveliness 中，automatic 发布端也不能满足 manual-by-topic 的请求。官方 Humble 兼容性表

3.2 两个容易过度推广的结论

误区一：双方 depth 不一样就无法通信。

深度主要影响各自缓存，并不要求双方写同一个数字。发布端深度 10、订阅端深度 1，可以是有意设计的“发送端保留一定历史，接收端只缓存最新”。

误区二：一个话题已经有订阅者收到数据，说明所有订阅者都能收到。

每对 publisher/subscription 分别匹配。例如同一个 reliable publisher，可以连上一个 best-effort 监视器和一个 reliable 记录器；但将 publisher 改为 best effort 后，记录器可能失配，监视器仍正常。

此外，“兼容”只表示允许建立通信，不保证网络可达、类型正确、Executor 被调度或者回调逻辑没有异常。

下面是官方 Humble RMW 定义中的关键字段，不是所有 ROS 版本的永久承诺：

Profile History / Depth Reliability Durability 常见入口
default KEEP_LAST / 10 RELIABLE VOLATILE rclcpp::QoS(10)
sensor_data KEEP_LAST / 5 BEST_EFFORT VOLATILE rclcpp::SensorDataQoS()
services_default KEEP_LAST / 10 RELIABLE VOLATILE 默认服务请求与应答配置

这些普通 profile 的 deadline、lifespan、lease duration 使用默认时长值，liveliness 使用 system default。注意三个修正：SensorData 不是 depth 1，普通服务不是 depth 1，Parameter Events 也不是 KEEP_ALL 或默认持久化快照。Humble qos_profiles.h 定义

如果要“当前有哪些参数”，应查询参数服务，而不是启动后只监听 /parameter_events 并假定已经得到了所有历史。

4.1 QoS(10) 与 SensorDataQoS() 不是一回事

rclcpp::QoS 的构造器、keep_last()、best_effort()、transient_local() 等链式配置可以在 Humble API 中核对。C++ 的 volatile 是关键字，因此方法叫 durability_volatile()。rclcpp Humble QoS API

4.2 Action 不是“一个 Reliable + Depth 10 的话题”

Action 包含 goal、cancel、result 三类服务，以及 feedback、status 两类话题。它们承担的角色不同，因此不能用一行 QoS 描述整个 Action。

例如目标已经接受，不代表结果已经成功；反馈暂时缺失，也不能简单等同于目标被取消。排查 Action 应分别看服务调用、反馈和状态端点，再检查客户端/服务端生命周期。Humble rcl_action 客户端端点与默认选项

下面都是评估起点，不是“这个话题必须永远如此”的规定。最终应与实际驱动、控制器接口契约和测量结果一致。

5.1 感知链路：允许丢帧，不等于允许瞎丢信息

检测器跳过几张图像可能只是帧率降低；IMU 预积分少一段采样，误差却可能被持续带入状态估计。应区分“业务允许少处理一些帧”和“算法假定每个样本都在”。

图像、点云还有一个容量问题：一帧未压缩 1920 × 1080 × 3 的图像约为 6.2 MB，30 Hz 仅像素载荷就约 187 MB/s。深度 10 的样本载荷就可能达到约 62 MB，还没计算不同端点的缓存、序列化和应用副本。这个估算说明为什么“先把所有队列调大”通常需要成本评估。

5.2 连续控制：新鲜的零速度，胜过过期的可靠速度

假设遥控端 20 Hz 发指令，业务要求超过 250 ms 没有有效新指令就进入安全策略。一个合理的设计讨论应包括：

  1. VOLATILE，避免新启动消费者补收旧动作意图。
  2. 小深度，让待处理的设定值不过度堆积。
  3. 若带时间戳，检查生成时间、允许年龄和时钟关系。
  4. 使用本机单调时钟记录“最后一次接受有效指令”的时间。
  5. Watchdog 超时后执行明确的停止/保持/降级状态，而不是继续沿用旧指令。
  6. 收到新包不一定刷新 watchdog：NaN、越界、过期、来源非法的指令应拒绝。
  7. 底层驱动器还应有自己的通信超时和急停机制。

这里的 20 Hz、250 ms 都是教学假设，不能直接作为某台机械臂、无人机或移动机器人的安全阈值。飞行器失联时尤其不能把“所有输出归零”当成普适安全策略。

5.3 QoS 与控制循环不要揉成一个概念

在典型 ros2_control 系统中，订阅回调接收目标，控制循环读取状态、执行 controller update、写硬件命令。QoS 是目标如何进入系统的一部分，不等于每个电机都必须通过 DDS 跑一次 PID。

多线程 Executor 也不能替代 QoS：它可能改善回调互相阻塞的问题，但不能让不兼容的端点互通，也不能让已经过期的消息重新有效。完整分工见控制器与硬件接口专题。

7.1 这个 Watchdog 为什么还不能用于真机安全

演示只验证“回调收到数据”的间隔，没有验证消息内容和采样年龄。而且 timer 与 subscription 仍在同一 Executor 中：如果执行线程卡住，watchdog 回调也可能一起卡住。

示例的 create_timer() 默认还使用节点时钟。若开启 use_sim_time 并暂停 /clock，定时器可能不再触发，即使回调内部用的是 monotonic，检查也无从执行。需要按真实时间运行的监控，应另外选择合适的定时器时钟及执行线程，并单独验证暂停和时钟跳变行为。

真正的控制系统要定义哪些检查进入独立的控制循环，哪些由驱动器或硬件承担。使用多线程也必须考虑 callback group、锁竞争和调度延迟，不能因为换了 Executor 就声称已经具有硬实时保护。

7.2 跨机器算消息年龄要先解决时钟

“当前 ROS 时间 - header.stamp”只有在时间域和同步关系成立时才有意义。应分别考虑：

  • 两台实体计算机的时钟同步误差。
  • use_sim_time 是否一致，/clock 是否在推进。
  • rosbag 回放是否循环、暂停或改变时间。
  • 相机硬件时间戳有没有正确映射到 ROS 时间。
  • 零时间戳、未来时间戳和时钟跳变如何处理。

本机 time.monotonic() 适合判断本机接收间隔，不应写进消息后直接和另一台机器的 monotonic 值相减。

10.2 /tf 与 /tf_static 不能合并理解

动态 TF 描述随时间变化的位姿；静态 TF 描述固定关系，通常需要支持晚加入读者。应优先使用 tf2_ros 官方 broadcaster/listener，保留它们为不同端点设计的 QoS。

不要因为“静态 TF 用 transient local”，就把动态 /tf 也机械地改成同样的深度和持久性；更不要把多个独立变换当成一个 String 快照简单覆盖。TF 消息内容、发布端的变换集合维护以及消费者的时间缓存，还各有语义。Humble TF QoS 定义、静态 TF broadcaster 接口

10.3 YAML 不是所有节点都自动接受的万能覆盖

rosbag2 的 override 是 rosbag2 明确提供的功能。第三方驱动是否允许通过参数改 QoS、参数叫什么、何时生效，应看它自己的接口文档和实际端点。

因此修改配置后要重新运行 ros2 topic info --verbose 检查，而不是因为 YAML 文件里出现了 reliable 就认为 DDS 端点已经改变。某些配置只在实体创建时读取，需要重建节点或重新配置生命周期；不要假定运行时 ros2 param set 总能修改已存在的 publisher。

11. 按证据排障，不靠随机切换 Reliable

11.1 第一层：实体能否互相发现

环境变量为空不代表没有使用默认值；要结合发行版、启动环境和节点报告解释结果。检查 namespace、remap、消息类型和多个同名节点，再看容器网络、DDS 发现配置、防火墙、多播等问题。

如果根本发现不到端点，先查发现与网络，不要从 deadline 开始改。

11.2 第二层：逐对比较实际 QoS

重点抄下：reliability、durability、history/depth、deadline、liveliness、lease duration。一个话题可能有多个 publisher；不要只看第一段输出就结束。

建立兼容关系后，再检查端点连接数量、incompatible QoS 事件和显式 profile 的 echo 结果。

11.3 第三层：消息是否新鲜、回调是否被调度

观察到的现象 优先检查
Topic 可见，自己收不到，echo 却能收到 Echo 自动适配与自己请求的 QoS 是否不同
普通回调能收到，同步回调没有执行 时间戳、同步窗口、各输入 subscription QoS
一开始正常，运行后越来越滞后 消费吞吐、DDS/应用队列、回调耗时
发布端已经停了，控制器还在运动 是否仍使用旧目标，watchdog 是否实际执行
Reliable 后 CPU/延迟明显增加 丢包、重传、慢读者、资源与带宽瓶颈
Deadline 没有报警但处理已超时 监测的是数据到达还是应用执行；事件回调是否饥饿
重启 RViz 后看不到静态内容 发布端仍否存活、双方 durability、历史是否完整
Bag 有数据，回放消费者收不到 回放 publisher QoS、模拟时间、消费者是否激活

ros2 topic hz 测到的是该工具观察到的到达频率，不自动等于传感器真实采样频率，也不表示用户自己的回调具有同样表现。终端打印大图像/点云还会干扰观察，应尽量使用计数和统计而不是逐字段刷屏。Humble topic hz 实现与说明

12. 选型检查单与复习题

12.1 上线前的 QoS 检查单

  • [ ] 区分连续设定值、一次性任务、状态流和完整快照。
  • [ ] 明确数据能丢多少、能旧多久、晚加入者需要什么。
  • [ ] 记录每个关键端点的实际 profile，不仅记录 preset 名称。
  • [ ] 验证可靠性、持久性、deadline 和 liveliness 相关兼容性。
  • [ ] 估算缓存字节数，测量处理吞吐，不把大 depth 当作性能优化。
  • [ ] 检查采样时间域、跨机同步和回放时钟。
  • [ ] 将通信活跃、应用响应和硬件执行成功分开监测。
  • [ ] 对控制指令定义拒绝条件、有效期、失联状态和恢复条件。
  • [ ] 验证 rosbag 录制与回放，记录丢样和端点配置。
  • [ ] 验证所选 RMW 的事件能力；没有事件不等于没有故障。
  • [ ] 在目标架构和真实负载下重新测量，而不是只在空载 echo 中验收。

12.2 用自己的话回答这六个问题

  1. 为什么 SensorDataQoS() 发布的图像，QoS(10) 订阅可能收不到？
  2. 为什么地图 publisher 是 transient local，但 volatile 订阅仍不应依赖补到旧地图？
  3. 发布端 deadline 10 ms、订阅端 deadline 30 ms 是否匹配？反过来呢？
  4. 数据 100 Hz 到达、算法只能 20 Hz 处理，把 depth 从 5 调到 100 解决了什么，又引入了什么？
  5. Deadline、Liveliness 和本机接收 watchdog，哪一个能够直接证明电机安全？
  6. 为什么把 rosbag 回放改成 reliable，不能补回原录制阶段丢失的数据？

对应的核心答案是：端点需求高于供给、历史请求不同、提供间隔必须足够短、缓存不增加吞吐、三者都不能独自证明硬件安全，以及回放只能提供已经记录的数据。
